# /ingest：inbox → 逐篇筆記 → 整合提案

流程分兩段，中間要等使用者：

1. **整理**：inbox 原檔 → 逐篇筆記 + 提案檔。
2. **套用**：使用者回覆提案後，修改知識頁。

使用者有回覆、但提案還沒套用的話，直接跳到「二、套用提案」。

## 一、整理

### 1. 找出要處理的檔案

- `inbox/` 底下除了 `_template.md` 以外的所有檔案都是待處理的（整理完會刪，所以留著的都是還沒處理的）。
- 一次處理一個檔案；有多個就依日期由舊到新逐一處理，每篇各自走完第 2–6 步。
- 使用者直接在對話中貼筆記也照同樣流程，只是沒有原檔要刪。
- frontmatter 缺 `date`、`type`、`event` 的話，能從內文推斷就推斷，推斷不出來就先問。

### 2. 分辨四種內容

使用者的筆記混雜四種內容。分類只是給你參考，使用者寫在哪一區不一定準：

| 種類 | 特徵 | 怎麼處理 |
|---|---|---|
| 速記 | 只有關鍵字或片段 | 補成完整內容。補寫的部分包在 `:::supplement` 裡，和講者實際講的內容分開 |
| 重點 | 已經記得比較完整 | 整理語句、修正格式，不改原意 |
| 查閱資料 | 直接貼上的網頁、指引、文獻，格式雜亂 | 重組成條列，保留來源網址（寫成連結） |
| 心得 | 講者的經驗、觀點，或使用者自己的想法 | 寫成敘述文，標明是誰的觀點 |

速記補寫原則：只補醫學上已有共識的內容；數字、門檻、新指引這類不確定的細節要查證，查不到就包 `:::verify`。逐篇筆記是知識頁 `:::source` 的唯一出處，講者講的和 Claude 補的一定要分得出來。

### 3. 寫成逐篇筆記

存到 `frontend/content/journal/<YYYY>/<YYYYMMDD>-<英文 slug>.md`，slug 簡短、小寫、用連字號。

```yaml
---
title: 中文標題，點出主題（例：Type 2 MI 的診斷與處置）
date: 2026-10-20
time: "14:00"        # 有就寫
type: rounds         # 照抄 inbox
event: 心臟內科 Grand Round
speaker: 王醫師       # 多位用陣列
place: …             # 有就寫，地點可公開
tags: [心臟內科, ACS, 指引更新]
integrated: false    # 提案套用（或確定不必整合）後改 true
---
```

內文結構：

1. `## 摘要`：兩三句話說明這場的主題和最重要的收穫。
2. 主題段落（h2／h3，**子彈式**）：速記、重點、查閱資料**依邏輯重組**，不照記錄的時間順序。可以用表格、`:::exam`、`:::pitfall`、`:::compare`、流程圖，格式規範同知識頁（見藍圖 §4、CLAUDE.md）。
3. `## 心得`（**敘述文**，分段，不用條列）：講者的觀點寫「王醫師認為…」，使用者自己的想法寫「我的想法：…」或另開 h3「我的想法」。

疾病、檢查、藥物第一次出現時用 wiki-link 連到知識頁（`[[諸病微精/心臟內科#…|…]]`），連得到才連。

### 4. 標籤

- 分三種，每篇大約 3–6 個：
  - 科別：心臟內科、藥理學……，用 `data/nav.js` 裡的頁名。
  - 主題：疾病、藥物、檢查，例如 ACS、抗凝血劑。
  - 性質：指引更新、臨床技巧、考點、病例、個人經驗。
- 下標籤前先看既有標籤，能沿用就沿用，不要另造同義詞：
  `grep -rh "^tags:" frontend/content/journal`
- 縮寫統一用大寫英文（ACS、AKI），沒有通用縮寫的用中文。

### 5. 去識別化

- 講者、地點、醫院、活動名稱都**可以公開**。
- 要去識別化的只有**病人**：姓名、病歷號、床號、生日、確切就診日期、可辨識的罕見特徵組合、可辨識的影像。年齡改寫成區間（60 多歲）。
- 有拿不準的地方，**寫進 content/ 之前先問**。content/ 會進公開的 git，一旦 commit 就刪不掉。

### 6. 寫整合提案檔

存到 `temp/proposals/<與逐篇筆記同檔名>.md`：

```markdown
# 整合提案：<逐篇筆記標題>

逐篇筆記：`frontend/content/journal/<YYYY>/<檔名>.md`
回覆方式：勾選要做的 [x]、刪掉不要的、在項目下方直接寫意見；或在對話中回答。回覆後跟 Claude 說「套用提案」。

## 新重點（插入知識頁）
- [ ] [[諸病微精/心臟內科#Type 2 MI]]：在「治療」後插入「…」（包 `:::source{from="<檔名>"}`）

## 細節（折疊或子頁）
- [ ] [[…]]：包成 `:::detail{title="…"}`「…」

## 衝突（需要你決定）
- [ ] [[…]]：現有內容寫 X，講者說 Y（依據：…），以哪個為準？

## 只留在逐篇筆記
- 心得、個人經驗、和既有內容重複的部分……（不需回覆）
```

- 每條都要寫清楚**哪一頁哪一段、插入什麼文字**，讓使用者不用打開知識頁就能判斷。
- 目標段落還不存在（例如該分類尚未撰寫）時，提案寫「等 <頁面> 建立時納入」，不另外新開頁面。
- 完全沒有可整合的內容時，不寫提案檔，`integrated` 直接設 true。

### 7. 收尾

1. 跑 `cd frontend && npm run build`，看有沒有失效連結。
2. 回報：逐篇筆記的路徑、標籤、補寫的段落、提案檔的路徑和摘要（共幾條、衝突幾條），並請使用者看過逐篇筆記。
3. 記進 `UPDATE.md`、commit（不 push）。
4. **使用者確認逐篇筆記沒問題後**，才刪掉 inbox 原檔（不進 git，刪了救不回來），然後告訴使用者已刪除。

## 二、套用提案

1. 讀提案檔與使用者的回覆（勾選、刪除、意見，或對話中的回答）。
2. 修改知識頁：勾選的項目照做，插入的段落包 `:::source{from="<逐篇筆記檔名>"}`；衝突依使用者的決定處理。
3. 逐篇筆記改成 `integrated: true`（「已整合至」清單由建置時掃描 `:::source` 自動產生，不用手填）。
4. 刪除提案檔，build 確認，記進 UPDATE.md、commit。

## 提醒

只要 `temp/proposals/` 裡還有提案檔，每次對話開頭和每則回覆結尾的「還沒做」清單都要列出來，請使用者回覆。
