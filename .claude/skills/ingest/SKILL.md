# /ingest：inbox → 逐篇筆記 → 整合提案

流程分兩段，中間要等使用者：

1. **整理**：inbox 原檔 → 逐篇筆記 + 提案檔。
2. **套用**：使用者回覆提案後，修改知識頁。

使用者有回覆、但提案還沒套用的話，直接跳到「二、套用提案」。

## 一、整理

### 0. 從 phantomajor 收件匣抓筆記

使用者平常在 phantomajor 的 `/m/inbox` 用表單記筆記（可附照片），暫存在 Supabase。先執行：

```bash
cd frontend && npm run pull-inbox
```

- 每篇寫成 `inbox/<YYYYMMDD>-<HHmm>-<id 前 6 碼>.md`（格式同範本：frontmatter 多一行 `source:` 註明來自收件匣，內文只有一個「筆記」區；舊格式的四區會接成【速記】【重點】這類小標），照片存在同名資料夾（`01.jpg`、`02.jpg`…，編號就是內文 `[圖 N]` 的 N），檔案末尾的「照片」區列出每張照片的說明。
- 寫入成功的筆記會從 Supabase 刪除；失敗的不刪，訊息會列出來，下次重抓。
- 收件匣是空的、或腳本出錯（密語、SQL）時照常處理 `inbox/` 裡既有的檔案，並把錯誤告訴使用者。
- 腳本與 SQL 見 `frontend/scripts/pull-inbox.mjs`、phantomajor 的 `backend/supabase/m/`、藍圖 phantomajor `frontend/blueprints/m/m_v1.md`。

### 1. 找出要處理的檔案

- `inbox/` 底下除了 `_template.md` 以外的所有 `.md` 檔都是待處理的（整理完會刪，所以留著的都是還沒處理的）；同名資料夾是它的照片。
- 一次處理一個檔案；有多個就依日期由舊到新逐一處理，每篇各自走完第 2–6 步。
- 使用者直接在對話中貼筆記也照同樣流程，只是沒有原檔要刪。
- frontmatter 缺 `date`、`type`、`event` 的話，能從內文推斷就推斷，推斷不出來就先問。

### 2. 分辨四種內容

使用者的筆記不分區，四種內容混在一起，要自己分辨（有【速記】這類小標或（講者）（我）標記時可以參考，但不一定準）：

| 種類 | 特徵 | 怎麼處理 |
|---|---|---|
| 速記 | 只有關鍵字或片段 | 補成完整內容。補寫的部分包在 `:::supplement` 裡，和講者實際講的內容分開 |
| 重點 | 已經記得比較完整 | 整理語句、修正格式，不改原意 |
| 查閱資料 | 直接貼上的網頁、指引、文獻，格式雜亂 | 重組成條列，保留來源網址（寫成連結） |
| 心得 | 講者的經驗、觀點，或使用者自己的想法 | 寫成敘述文，標明是誰的觀點 |

速記補寫原則：只補醫學上已有共識的內容；數字、門檻、新指引這類不確定的細節要查證，查不到就包 `:::verify`。逐篇筆記是知識頁 `:::source` 的唯一出處，講者講的和 Claude 補的一定要分得出來。

### 3. 寫成逐篇筆記

存到 `frontend/content/journal/<YYYY>/<YYYYMMDD>-<英文 slug>.md`，slug 簡短、小寫、用連字號。

```yaml
---
title: 中文標題，點出主題（例：Type 2 MI 的診斷與處置）
date: 2026-10-20
time: "14:00"        # 有就寫
type: morning        # 照抄 inbox
event: 心臟內科 Grand Round
speaker: 王醫師       # 多位用陣列
place: …             # 有就寫，地點可公開
tags: [心臟內科, 指引更新]
integrated: false    # 提案套用（或確定不必整合）後改 true
---
```

內文結構：

1. `## 摘要`：兩三句話說明這場的主題和最重要的收穫。
2. 主題段落（h2/h3，**子彈式**）：速記、重點、查閱資料**依邏輯重組**，不照記錄的時間順序。可以用表格、`:::exam`、`:::pitfall`、`:::compare`、流程圖，格式規範同知識頁（見藍圖 §4、CLAUDE.md）。
3. `## 心得`（**敘述文**，分段，不用條列）：講者的觀點寫「王醫師認為…」，使用者自己的想法寫「我的想法：…」或另開 h3「我的想法」。
   - **心得先不放進逐篇筆記**：寫在提案檔的「心得（請確認）」段，附上說明（哪些是依速記改寫、哪些是 Claude 自己寫的、更正了哪些錯字、哪裡不確定原意），使用者確認後才放進筆記最後。速記的解讀可能出錯（例如把順帶提到的新聞當成討論的個案），心得最容易放大這種誤讀。
   - 速記提到的新聞、事件只有關鍵字時，查出新聞內容寫成一點（附來源），不要猜它在討論中的角色；個案討論的個案以使用者提供的投影片或資料為準。

疾病、檢查、藥物第一次出現時用 wiki-link 連到知識頁（`[[諸病微精/心臟內科#…|…]]`），連得到才連。

### 3.1 照片

收件匣筆記可能附照片（投影片、白板、講義）。每張照片：

1. 用 Read 看照片內容，對照說明與內文的 `[圖 N]` 標記，決定放在逐篇筆記的哪一段。沒有標記的照片依內容判斷位置；跟主題無關或拍壞的照片不用，回報時說明。
2. 去識別化：照片裡有病人的臉、姓名、病歷號、床號、螢幕上的病人資料時，裁掉；裁不掉就不用。拿不準先問。
3. 決定裁切範圍（只留有用的部分，去掉投影幕外的背景、別人的頭），用原圖像素座標：
   ```bash
   cd frontend
   node scripts/process-photo.mjs ../inbox/<資料夾>/01.jpg --info   # 原圖尺寸
   node scripts/process-photo.mjs ../inbox/<資料夾>/01.jpg media/journal/<YYYY>/<逐篇筆記檔名>-1.webp --crop=左,上,寬,高
   ```
   腳本會轉正方向、縮到長邊 1600 px、轉 WebP，存進 `public/media/`。裁完用 Read 看一次輸出的圖，確認沒裁錯。
   - 斜拍的投影片、白板（拍成梯形）：改用 `--perspective=左上x,左上y,右上x,右上y,右下x,右下y,左下x,左下y` 給投影幕四個角的原圖座標，拉成正面的長方形，不用再 `--crop`。
   - 只是整張歪掉（邊緣是平行的但傾斜）：用 `--rotate=度`（順時針為正）扶正，空角補白；接著的 `--crop` 座標以旋轉後的圖為準，先用 `--info --rotate=度` 看尺寸。
   - 座標估不準時先輸出一次、用 Read 看結果再微調，四邊還留有背景或切到內容就修正座標重跑。
4. 在筆記中用 `![替代文字](media/journal/<YYYY>/<檔名>-1.webp "圖說（來源：王醫師投影片）")` 嵌入，圖說附來源；`[圖 N]` 標記本身不留在筆記裡。
5. 投影片內容如果是文字或表格，除了放圖，重點也要寫進內文（圖不會被搜尋到）。

### 4. 標籤

標籤只用兩份固定清單（`frontend/data/tags.js`），避免越下越多：

- **科別** 1–2 個：基礎醫學與諸病微精的頁名（感染科、藥理學、公共衛生……），清單跟著 `data/nav.js` 自動更新。
- **性質** 0–2 個：指引更新、臨床技巧、考點、病例、法規、個人經驗。
- 疾病、藥物、檢查這類**主題詞不下標籤**：它們已經在內文與標題裡（全站搜尋找得到），第一次出現時也連到知識頁。
- 清單裡沒有適合的性質時，不要自己加：回報時提議新的性質名稱，使用者同意後才加進 `data/tags.js`。
- 建置時不在清單裡的標籤會在 console 警告，`/journal` 篩選列會把它放在「其他」。

### 5. 去識別化

- 講者、地點、醫院、活動名稱都**可以公開**。
- 要去識別化的只有**病人**：姓名、病歷號、床號、生日、確切就診日期、可辨識的罕見特徵組合、可辨識的影像。年齡改寫成區間（60 多歲）。
- 有拿不準的地方，**寫進 content/ 之前先問**。content/ 會進公開的 git，一旦 commit 就刪不掉。

### 6. 寫整合提案檔

存到 `temp/proposals/<與逐篇筆記同檔名>.md`：

```markdown
# 整合提案：<逐篇筆記標題>

逐篇筆記：`frontend/content/journal/<YYYY>/<檔名>.md`
回覆方式：留著的項目照做，不要的直接刪掉，有意見寫在項目下方；或在對話中回答。回覆後跟 Claude 說「套用提案」。

## 新重點（插入知識頁）
- [[諸病微精/心臟內科#Type 2 MI]]：在「治療」後插入「…」（包 `:::source{from="<檔名>"}`）

## 細節（折疊或子頁）
- [[…]]：包成 `:::detail{title="…"}`「…」

## 衝突（需要你決定）
- [[…]]：現有內容寫 X，講者說 Y（依據：…），以哪個為準？

## 從知識頁連到逐篇筆記
- [[…]]：段落末尾加一行「- 詳見 [[<檔名>|<逐篇筆記標題>]]（逐篇筆記）」（理由：…，內容太瑣碎、不整合進知識頁）

## 只留在逐篇筆記
- 心得、個人經驗、和既有內容重複的部分……（不需回覆）
```

- 每條都要寫清楚**哪一頁哪一段、插入什麼文字**，讓使用者不用打開知識頁就能判斷。
- 太瑣碎、不值得寫進知識頁，但讀到相關段落的人會想看的內容（獨立的討論、個案、在地做法），放進「從知識頁連到逐篇筆記」，不必是知識頁裡已經提到的詞。
- 目標段落還不存在（例如該分類尚未撰寫）時，提案寫「等 <頁面> 建立時納入」，不另外新開頁面。
- 完全沒有可整合的內容、也沒有心得時，不寫提案檔，`integrated` 直接設 true；有心得就一定要有提案檔。
- 提案檔加一段「## 心得（請確認後才放進逐篇筆記）」，放心得的草稿與說明。

### 7. 收尾

1. 跑 `cd frontend && npm run build`，看有沒有失效連結。
2. 回報：逐篇筆記的路徑、標籤、補寫的段落、提案檔的路徑和摘要（共幾條、衝突幾條），並請使用者看過逐篇筆記。
3. 記進 `UPDATE.md`、commit（不 push）。
4. **使用者確認逐篇筆記沒問題後**，才刪掉 inbox 原檔與同名照片資料夾（不進 git，刪了救不回來；收件匣的筆記在 Supabase 已經刪了，這是唯一的原始檔），然後告訴使用者已刪除。

## 二、套用提案

1. 讀提案檔與使用者的回覆（刪除、意見，或對話中的回答）。提案檔不用勾選框：留在檔案裡的項目就是要做的，被刪掉的就是不要。
2. 修改知識頁：留下的項目照做（有意見的依意見調整），插入的段落包 `:::source{from="<逐篇筆記檔名>"}`；衝突依使用者的決定處理。
3. 確認過的心得放進逐篇筆記最後的 `## 心得`。
4. 逐篇筆記改成 `integrated: true`（「已整合至」清單由建置時掃描 `:::source` 自動產生，不用手填）。
5. 刪除提案檔，build 確認，記進 UPDATE.md、commit。

## 提醒

只要 `temp/proposals/` 裡還有提案檔，每次對話開頭和每則回覆結尾的「還沒做」清單都要列出來，請使用者回覆。
